# Технический SEO-аудит сайта task.by (ЗАСО «ТАСК»)

**Дата аудита:** 28.07.2026
**Объект:** https://task.by/ — сайт страховой компании ЗАСО «ТАСК», Республика Беларусь
**Платформа:** 1С-Битрикс (Bitrix Site Manager), серверный рендеринг HTML (не SPA)

## Методология

Аудит выполнен вручную по «сырому» HTML, отдаваемому сервером (`curl -sL`), без использования браузера — сайт полностью серверно-рендерится, поэтому это надёжный метод для данной платформы. Дополнительно использованы:

- готовые данные краулинга — `report/pages.txt` (25 ключевых URL сайта);
- отчёты Lighthouse/PageSpeed Insights (мобайл + десктоп) — `report/psi-reports/*.json` и `report/summary.csv`;
- данные GTmetrix — `report/gtmetrix-summary.json`;
- прямые проверки `robots.txt`, `sitemap.xml` и обеих вложенных карт сайта (`sitemap-files.xml`, `sitemap-iblock-2.xml`);
- проверка HTTP-статусов и цепочек редиректов (`curl -sIL`, `curl -w "%{http_code}"`) для всех 202 URL, перечисленных в обеих sitemap-картах, и для ~20 дополнительных внутренних ссылок и вложений.

**Проанализировано детально:** 18 страниц из полного списка в `report/pages.txt`, включая главную, все разделы «Физическим лицам» и «Юридическим лицам» (включая дочерние страницы продуктов), «О компании», «Контакты», «Пресс-центр» (новости, конкретная статья, FAQ), «Страховой случай» и личный кабинет. Дополнительно точечно проверены ещё 6 страниц из списка (`/person/property`, `/person/health`, `/corporate/transport`, `/corporate/health`, `/corporate/property`, `/corporate/responsibility`) — то есть фактически охвачены все 25 URL из `pages.txt`.

Важное наблюдение по методологии: **Lighthouse SEO-скор равен 100/100 на всех 25 страницах (мобайл и десктоп)** — см. `report/summary.csv`. Однако Lighthouse проверяет каждую страницу изолированно и не умеет обнаруживать: дублирование контента/метатегов между разными URL, качество и валидность микроразметки, редиректы на «не ту» страницу, устаревшие форматы разметки. Именно эти классы проблем и составляют основную часть настоящего отчёта — они не видны в автоматическом скоре, но реально влияют на ранжирование и представление сайта в поиске.

## 1. Метаданные (title, description, canonical, robots, OG)

### 1.1 Meta description на 100% идентичен на всех страницах сайта

**Серьёзность:** Critical

**Затронутые страницы:** site-wide — подтверждено на всех 18 детально проверенных URL (главная, /person, /person/auto, /person/auto/osago, /person/auto/kasko, /person/property/house, /person/health/abroad, /corporate, /corporate/property/strahovanie_imuschestva, /corporate/responsibility/cmr, /about, /contact, /press_centr, /press_centr/news, /press_centr/faq, /strahovoj_sluchaj, /personal и т.д.)

**Доказательство:**
На каждой из 18 страниц найден побайтово идентичный тег (191 символ):
```html
<meta name="description" content="Страховая компания «ТАСК» предлагает широкий спектр услуг: страхование рисков, автомобиля (Каско, «зеленая карта»), имущества, гражданской ответственности, грузов, медицинская страховка и др." />
```
Это подтверждено и для главной, и для узкоспециализированной страницы продукта «АвтоКаско» (`/person/auto/kasko`), и для страницы конкретной новости — везде текст совпадает символ в символ.

**Объяснение:** Meta description не подставляется индивидуально для каждой страницы/продукта — используется единственный статический текст компании, вписанный в шаблон.

**Бизнес-влияние:** В сниппете поисковой выдачи по запросам «КАСКО ТАСК», «ОСГО ТАСК», «страхование имущества дома» и т.д. пользователь видит один и тот же общий текст про компанию, а не про конкретный продукт, который искал — это снижает CTR и релевантность сниппета запросу.

**SEO-влияние:** Google по умолчанию переписывает description по своему усмотрению, если считает исходный нерелевантным — то есть компания фактически теряет контроль над сниппетом почти на всех страницах. Кроме того, дублирование description на масштабе всего сайта — классический сигнал шаблонного/малоценного контента.

**Рекомендация:** Прописать уникальный, отражающий суть продукта description (150–160 символов) для каждой из ключевых страниц минимум для 25 URL из `pages.txt`, в дальнейшем — для всех продуктовых карточек и новостей.

### 1.2 Полное дублирование title/H1 между родительской и дочерней страницами (см. также раздел 8 «Контент»)

**Серьёзность:** Critical

**Затронутые страницы:**
- `https://task.by/person` и `https://task.by/person/property` — title и H1 идентичны: «Имущество»
- `https://task.by/corporate` и `https://task.by/corporate/transport` — title и H1 идентичны: «Транспорт»
- Также title/H1 «Имущество» повторяется третий раз на `https://task.by/corporate/property`

**Доказательство:**
```
https://task.by/person                  TITLE: Имущество | ЗАСО «ТАСК»   H1: Имущество
https://task.by/person/property         TITLE: Имущество | ЗАСО «ТАСК»   H1: Имущество
https://task.by/corporate/property      TITLE: Имущество | ЗАСО «ТАСК»   H1: Имущество

https://task.by/corporate               TITLE: Транспорт | ЗАСО «ТАСК»  H1: Транспорт
https://task.by/corporate/transport     TITLE: Транспорт | ЗАСО «ТАСК»  H1: Транспорт
```
Побайтовое сравнение (`diff`) HTML `/person` и `/person/property`, а также `/corporate` и `/corporate/transport` показало различие только в 16 строках — и все различия сводятся к CSRF-токенам сессии (`bitrix_sessid`, `PHPSESSID`, `captcha_sid`). Остальной контент, включая title, meta description, H1 и весь текст страницы, побайтово совпадает.

**Объяснение:** Родительские страницы разделов «Физическим лицам» (`/person`) и «Юридическим лицам» (`/corporate`) не являются самостоятельными обзорными лендингами — движок отдаёт на них ровно тот же контент, что и на первую дочернюю подкатегорию («Имущество» и «Транспорт» соответственно). Это два независимо индексируемых URL с идентичным содержимым, title, H1, description и без rel=canonical, указывающего, какой из них считать основным (см. проблему 1.4).

**Бизнес-влияние:** Раздел «Физическим лицам» на сайте фактически не имеет собственной обзорной страницы — посетитель, ожидающий увидеть список всех продуктов для частных лиц, вместо этого попадает на страницу конкретного продукта «Имущество».

**SEO-влияние:** Классическая проблема дублированного контента (duplicate content) — два URL с одинаковым содержимым конкурируют за одни и те же ключевые слова (keyword cannibalization), Google выбирает один из них по своему усмотрению, теряется управляемость индексации и распределение ссылочного веса.

**Рекомендация:** Либо сделать `/person` и `/corporate` полноценными обзорными страницами с уникальным контентом (список всех продуктов раздела, вводный текст), либо, если такая архитектура намеренна, поставить `rel=canonical` с `/person` на `/person/property` (аналогично для corporate) — но первый вариант предпочтителен для SEO, так как эти URL являются наиболее вероятными посадочными для широких запросов.

### 1.3 Заголовок `<title>` главной страницы избыточно длинный

**Серьёзность:** Medium

**Затронутые страницы:** `https://task.by/`

**Доказательство:**
```html
<title>Страховая компания «ТАСК»: обязательное страхование, страховка авто, рисков, имущества, автомобиля (Каско), гражданской ответственности, грузов </title>
```
Длина строки — 143 символа (измерено программно, `len()` по декодированной строке).

**Объяснение:** Google отображает в сниппете практически не более ~55–60 символов (до ~600px) для кириллического текста, после чего строка обрезается многоточием.

**Бизнес-влияние:** Первый и самый важный сниппет сайта (главная страница по брендовым и общим страховым запросам) почти гарантированно обрезается в выдаче, из-за чего пользователь не видит вторую половину сообщения и, скорее всего, само название компании «ТАСК» уйдёт за пределы видимой части.

**SEO-влияние:** Обрезанный title снижает читаемость и CTR сниппета; кроме того, слишком длинный title размывает релевантность по конкретным ключевым словам (title пытается охватить сразу 6+ разных продуктов).

**Рекомендация:** Сократить до ~55–60 символов, например: `Страховая компания «ТАСК»: ОСАГО, КАСКО, страхование имущества и грузов`.

### 1.4 Отсутствует `rel=canonical` на всех страницах

**Серьёзность:** High

**Затронутые страницы:** site-wide, подтверждено на всех 18 проверенных URL.

**Доказательство:** Тег `<link rel="canonical" ...>` не найден ни на одной из 18 страниц (грепом по `<head>` каждого HTML-файла). Независимо это же подтверждает аудит Lighthouse: аудит `canonical` во всех `report/psi-reports/*.json` возвращает `"scoreDisplayMode": "notApplicable"` — то есть Lighthouse не нашёл canonical-тег, который можно было бы оценить.

**Объяснение:** Ни на одной странице сайта нет самоссылающегося (self-referencing) canonical URL.

**Бизнес-влияние:** Особенно критично на фоне проблемы 1.2 (полностью дублирующийся контент между `/person`/`/person/property` и `/corporate`/`/corporate/transport`) и известных в Bitrix «мусорных» параметрических URL (сортировки, фильтры, `?PAGEN`, `print=` и т.д., которые видны в `robots.txt`, но canonical всё равно является страховкой на случай, если такие URL всё же попадут в индекс, например через внешние ссылки).

**SEO-влияние:** Без canonical поисковик самостоятельно выбирает «основную» версию страницы среди дублей, что непредсказуемо и может размывать ссылочный вес между версиями.

**Рекомендация:** Добавить self-referencing `<link rel="canonical" href="https://task.by/полный-путь/">` на все страницы шаблона (это стандартная практика для Bitrix и решается на уровне шаблона сайта).

### 1.5 Полностью отсутствуют Open Graph и Twitter Card теги

**Серьёзность:** High

**Затронутые страницы:** site-wide — 0 тегов `og:*` и 0 тегов `twitter:*` найдено на всех 18 проверенных страницах.

**Доказательство:** Регулярное выражение по `<meta property="og:...">` и `<meta name="twitter:...">` не дало ни одного совпадения ни на главной, ни на карточках продуктов, ни на статье новости.

**Объяснение:** В `<head>` нет ни одного тега протокола Open Graph (og:title, og:description, og:image, og:url) и ни одного Twitter Card тега.

**Бизнес-влияние:** Для белорусского рынка это особенно ощутимо: ссылки на статьи и продукты активно репостятся в Viber, Telegram и соцсетях. Без og-тегов такие ссылки при вставке в мессенджер либо не формируют превью вообще, либо мессенджер сам выбирает произвольную картинку/текст со страницы — бренд теряет контроль над визуальным представлением ссылки и CTR по репостам падает.

**SEO-влияние:** Прямого влияния на ранжирование Open Graph не оказывает, но косвенно снижает социальные сигналы (переходы, вовлечённость), а также ухудшает индексацию превью в некоторых поисковых агрегаторах и мессенджерах, которые используют og:image/og:title как источник данных.

**Рекомендация:** Добавить как минимум `og:title`, `og:description`, `og:image`, `og:url`, `og:type` и `twitter:card` на все шаблоны, с уникальным og:image для новостных статей (по умолчанию — логотип/брендированная заглушка для остальных страниц).

### 1.6 Устаревший тег `<meta name="keywords">` на каждой странице

**Серьёзность:** Low

**Затронутые страницы:** site-wide.

**Доказательство:**
```html
<meta name="keywords" content="ТАСК, страховка, страховая компания, ОСАГО, гражданская ответственность, каско, «зеленая карта»,  имущество, автомобиль, риски, грузы" />
```
(главная); на внутренних страницах используется практически тот же общий набор ключевых слов, не специфичный для конкретной страницы (например, идентичный список "Страхование, ТАСК, страховка, страховая компания, ОСГО..." встречается на `/person/auto/osago`, `/person/auto/kasko`, `/person/property/house`, `/corporate`, `/about`, `/personal` и т.д.)

**Объяснение:** Google и Bing официально не используют meta keywords для ранжирования с 2009 года.

**Бизнес-влияние:** Минимальное — не несёт функциональной ценности, только увеличивает вес HTML и вносит путаницу при поддержке шаблона.

**SEO-влияние:** Нейтральное для ранжирования, но по сути мёртвый код.

**Рекомендация:** Можно удалить полностью без последствий для SEO; либо, если оставлять, — не тратить на это ресурсы редакторов.

## 2. Заголовки (H1–H6)

### 2.1 Пропуск уровня заголовков (H1 → H3, без H2) на карточках продуктов

**Серьёзность:** Medium

**Затронутые страницы:** `/person/auto/osago`, `/person/auto/kasko`, `/person/property/house`, `/person/health/abroad`, `/corporate/property/strahovanie_imuschestva`, `/corporate/responsibility/cmr`, `/about` — то есть большинство «глубоких» продуктовых страниц.

**Доказательство:** Пример структуры заголовков `/person/auto/kasko`:
```
<h1> АвтоКаско
<h3> Что покрывает:
<h3> Варианты страхования:
<h3> Программа «Оптимальное КАСКО»
<h3> Преимущества полиса КАСКО от ЗАСО «ТАСК»
<h3> Когда можно не обращаться в компетентные органы
<h3> Перечень необходимых документов
<h3> Страховой случай
<h3> Прикрепленные документы
```
Заголовков `<h2>` на странице нет вообще — сразу после H1 идут H3. Для сравнения, на `/contact` и `/strahovoj_sluchaj` иерархия построена правильно (H1 → H2 → H3).

**Объяснение:** Секции внутри продуктовых страниц используют `<h3>` вместо `<h2>`, что нарушает логическую вложенность документа (H2 полностью пропущен).

**Бизнес-влияние:** Минимальный прямой эффект для пользователя (визуально это не всегда заметно), но ухудшает семантическую структуру для скринридеров (доступность) и краулеров.

**SEO-влияние:** Google в целом устойчив к пропуску уровней, но чистая иерархия заголовков помогает лучше сегментировать содержимое страницы для featured snippets и понимания структуры контента — на 6+ страницах продуктов это системная недоработка шаблона.

**Рекомендация:** Привести иерархию к `H1 → H2 → H3` в шаблоне карточки продукта (замена тега `<h3>` на `<h2>` для заголовков секций верхнего уровня внутри контента).

### 2.2 Пустой тег `<h3>` без текстового содержимого

**Серьёзность:** Low

**Затронутые страницы:** `https://task.by/person/health/abroad`

**Доказательство:** В извлечённом списке заголовков страницы:
```
<h1> Страхование от внезапных заболеваний и несчастных случаев на время поездки за границу
<h3>                                            ← пустой, без текста
<h3> Страховые случаи
...
```

**Объяснение:** Верстка содержит пустой заголовочный тег, вероятно, оставшийся после правки контента редактором.

**Бизнес-влияние:** Незаметно для пользователя визуально, но засоряет DOM.

**SEO-влияние:** Незначительное — пустые заголовки не несут семантической пользы и слегка «размывают» структуру документа.

**Рекомендация:** Удалить пустой `<h3>` из содержимого страницы через административную панель Bitrix.

## 3. Изображения

Общее наблюдение (положительное): на всех 18 проверенных страницах атрибут `alt` присутствует у 100% тегов `<img>` (0 отсутствующих, 0 пустых) — это подтверждено и Lighthouse-аудитом `image-alt` (score: 1 на всех страницах). Проблема ниже касается не отсутствия alt, а качества его содержимого.

### 3.1 Keyword stuffing в атрибутах alt/title логотипа на каждой странице

**Серьёзность:** Medium

**Затронутые страницы:** site-wide — тег логотипа идентичен на всех проверенных страницах.

**Доказательство:**
```html
<img itemprop="logo" src="/local/templates/html_dev/images/logo.png"
     alt="ОСАГО, страхование рисков, автомобиля (Каско, «зеленая карта»), имущества, гражданской ответственности, грузов, медицинское и любая другая страховка"
     title="Полный спектр страховых услуг от ОСАГО и КАСКО до страховки имущества, здоровья и гражданской ответственности"/>
```

**Объяснение:** `alt` логотипа не описывает сам логотип (например, «Логотип ЗАСО ТАСК»), а вместо этого содержит перечисление всех продуктов компании — классический паттерн keyword stuffing, повторяющийся на каждой странице сайта, поскольку логотип выводится в шапке глобально.

**Бизнес-влияние:** Минимальное для конечного пользователя (виден только при наведении/для скринридеров), но выглядит непрофессионально при аудите/ручной проверке.

**SEO-влияние:** Такой паттерн формально противоречит рекомендациям Google по alt-тексту (описывать содержимое изображения, а не использовать его как площадку для ключевых слов); маловероятно, что несёт штрафные санкции, но и пользы не несёт — рискованная практика при масштабировании на весь сайт.

**Рекомендация:** Заменить alt логотипа на короткое описание, например `alt="ЗАСО «ТАСК» — страховая компания"`, оставив продуктовые ключевые слова для основного контента страниц.

## 4. Структурированные данные (Schema.org / JSON-LD / микроразметка)

### 4.1 Полное отсутствие JSON-LD; микроразметка Organization фрагментирована и неполна

**Серьёзность:** High

**Затронутые страницы:** site-wide — 0 блоков `application/ld+json` найдено на всех 18 проверенных страницах.

**Доказательство:** Вместо JSON-LD используется устаревшая микроразметка (`itemscope`/`itemtype`), причём разбитая на два независимых, не связанных между собой блока на каждой странице:

Блок 1 (шапка, логотип):
```html
<div class="logo" itemscope itemtype="http://schema.org/Organization">
  <a itemprop="url" href="https://task.by/">
    <img itemprop="logo" src="/local/templates/html_dev/images/logo.png" alt="..."/>
  </a>
</div>
```

Блок 2 (подвал, отдельный itemscope):
```html
<div class="contacts-foot" itemscope itemtype="http://schema.org/Organization">
  ...
  Адрес: <span itemprop="addressLocality">г. Минск,</span>
  <span itemprop="streetAddress"> ул. Червякова, 46, 220068</span>
  ...
  E-mail: <a href="mailto:info@task.by"><span itemprop="email">info@task.by</span></a>
</div>
```
При этом ни в одном из блоков нет `itemprop="name"` (название организации нигде не размечено как свойство Organization) и нет `itemprop="telephone"` — телефоны на `/contact` выведены обычным текстом без какой-либо разметки.

**Объяснение:** На странице фактически два разных `itemscope="Organization"` — ни один из них не является полным (логотип не привязан к адресу/email, а название организации не размечено вовсе). Search Console/парсеры структурированных данных, скорее всего, либо проигнорируют оба фрагмента как невалидные, либо соберут неполную сущность.

**Бизнес-влияние:** Компания не использует Knowledge Panel возможности Google (карточка организации в выдаче с телефоном, адресом, логотипом) — упущенная возможность для брендового трафика и локального SEO (у ТАСК десятки представительств по всей Беларуси, см. `/contact`).

**SEO-влияние:** Google рекомендует JSON-LD как основной формат структурированных данных; текущая микроразметка не проходит валидацию как полноценная сущность Organization, что снижает шансы на богатые результаты (rich results) и Knowledge Panel.

**Рекомендация:** Внедрить единый валидный блок JSON-LD `Organization` (или более специфичный `InsuranceAgency`) в `<head>` каждой страницы с полными данными: name, logo, url, telephone, address, sameAs (соцсети), и отдельно `LocalBusiness`/`PostalAddress` для каждого представительства на странице `/contact`.

### 4.2 Хлебные крошки размечены устаревшим data-vocabulary.org вместо schema.org BreadcrumbList

**Серьёзность:** High

**Затронутые страницы:** подтверждено как минимум на `/contact` (широко используется во всех шаблонах, где выводятся хлебные крошки).

**Доказательство:**
```html
<div class="breadcrumb">
  <ol class="list-reset">
    <li itemscope itemtype="http://data-vocabulary.org/Breadcrumb">
      <a href="/" title="Главная"><span itemprop="title">Главная</span></a>
    </li>
    <li itemscope itemtype="http://data-vocabulary.org/Breadcrumb">
      <a href="/contact/" title="Контактная информация"><span itemprop="title">Контактная информация</span></a>
    </li>
    <li itemscope itemtype="http://data-vocabulary.org/Breadcrumb" class="active">
      <span itemprop="title">Адреса и телефоны</span>
    </li>
  </ol>
</div>
```

**Объяснение:** `data-vocabulary.org` — формат разметки хлебных крошек, который Google официально прекратил поддерживать для отображения rich snippets ещё в 2020 году, полностью перейдя на `schema.org/BreadcrumbList`.

**Бизнес-влияние:** Косвенное — хлебные крошки в сниппете поиска (строка пути вместо длинного URL под заголовком) делают выдачу заметнее и понятнее пользователю; сайт лишён этого визуального преимущества в выдаче.

**SEO-влияние:** Прямая потеря rich-result «хлебные крошки» в поисковой выдаче Google — эта разметка попросту не читается современным парсером Google для данной цели.

**Рекомендация:** Заменить микроразметку на `schema.org/BreadcrumbList` (лучше всего — через JSON-LD, аналогично п. 4.1), либо как минимум сменить `itemtype` на `http://schema.org/BreadcrumbList` с соответствующими `itemprop="itemListElement"`.

### 4.3 FAQ-страница не размечена как FAQPage; вопросы — не заголовки, а ссылки аккордеона

**Серьёзность:** Medium

**Затронутые страницы:** `https://task.by/press_centr/faq`

**Доказательство:** Единственный заголовок на странице — H1 «Обязательное страхование гражданской ответственнности» (кстати, с опечаткой «ответственнности» — три «н»). Сами вопросы верстаются не заголовками, а ссылками аккордеона:

<div class="acc-heading" id="element-171618">

Разметки `itemtype="https://schema.org/FAQPage"`, `Question`, `acceptedAnswer`/`Answer` нет ни в микроразметке, ни в JSON-LD.

**Объяснение:** Вопросы и ответы физически присутствуют на странице (в свёрнутом аккордеоне), но не помечены семантически ни как заголовки (h2/h3), ни как структурированные данные FAQ.

**SEO-влияние:** Без разметки `FAQPage` страница не может претендовать на этот rich result, упуская возможность занять больше места в выдаче по информационным запросам («какие документы нужны для...», «что делать при ДТП» и т.п.).

**Рекомендация:** Добавить JSON-LD `FAQPage` с массивом `Question`/`acceptedAnswer`, соответствующим содержимому аккордеона; попутно исправить опечатку в заголовке H1 и пометить вопросы как `<h2>`/`<h3>` для внутренней структуры.

Без неё Google полагается только на внутренние ссылки и краулинговый бюджет, из-за чего индексация новых статей может занимать значительно больше времени или не происходить вовсе, особенно для менее авторитетных разделов сайта.

**Рекомендация:** Проверить и перезапустить механизм автогенерации sitemap в модуле «Карта сайта» Bitrix (обычно настраивается через cron/агент); убедиться, что `sitemap-iblock-2.xml` пересобирается регулярно (ежедневно/при публикации новой записи), а не вручную.

При этом `sitemap-files.xml` содержит:

### 5.4 robots.txt содержит устаревшую директиву `Host: www.task.by`

**Серьёзность:** Low

**Затронутые страницы:** `https://task.by/robots.txt` (весь сайт).

**Доказательство:**
```
User-Agent: *
Host: www.task.by
...
Sitemap: https://www.task.by/sitemap.xml
Sitemap: https://task.by/sitemap.xml
```
При этом фактическая проверка показала, что канонический домен — **без** `www`: `http://www.task.by/`, `https://www.task.by/` и `http://task.by/` все корректно отдают `301 → https://task.by/` (без www). То есть реальная канонизация домена настроена правильно, а вот директива `Host` в `robots.txt` указывает на противоположный (www) вариант домена.

**Объяснение:** Директива `Host` — нестандартная (не входит в протокол robots.txt), поддерживалась только Яндексом и была официально упразднена самим Яндексом в марте 2018 года; Google её никогда не поддерживал. Формально сейчас она ничего не делает, но по смыслу противоречит фактической настройке 301-редиректов (canonical-домен — без www).

**Бизнес-влияние:** Отсутствует — редиректы работают правильно, реальной дублирующей индексации www/non-www нет.

**SEO-влияние:** Минимальное — устаревшая директива просто игнорируется современными роботами, но вводит в заблуждение при ручном аудите файла и может запутать специалистов, поддерживающих сайт в будущем.

**Рекомендация:** Удалить строку `Host: www.task.by` и оставить в `robots.txt` только актуальный `Sitemap: https://task.by/sitemap.xml` (без www-варианта, раз канонический домен — без www).

## 6. Техническая индексируемость и внутренние ссылки

### 6.1 Критический баг редиректа: URL статей новостей (без слэша на конце) уводят не на статью, а на архив текущего года

**Серьёзность:** Critical

**Затронутые страницы:** вся секция `/press_centr/news/*` в «бесслэшевой» форме — подтверждено минимум на 2 независимых примерах из разных лет:
- `https://task.by/press_centr/news/2026/otpusk-zhivotnye-i-strakhovka` (эта же страница указана в `report/pages.txt` как одна из ключевых страниц сайта!)
- `https://task.by/press_centr/news/2024/poezdki-v-gruziyu`

**Доказательство:**
```
$ curl -sIL https://task.by/press_centr/news/2026/otpusk-zhivotnye-i-strakhovka
HTTP/2 301
location: https://task.by:443/press_centr/news/2026/
HTTP/2 200   (итоговая страница — архив новостей за 2026 год, НЕ сама статья)

$ curl -sIL https://task.by/press_centr/news/2024/poezdki-v-gruziyu
HTTP/2 301
location: https://task.by:443/press_centr/news/2026/     ← опять на архив 2026 (текущего) года, хотя статья 2024 года!
```
Это же независимо подтверждается собственными данными исходного аудита Lighthouse (`report/psi-reports/0022_press_centr_news_2026_otpusk-zhivotnye-i-strakhovka-mobile.json`):
```json
"requestedUrl": "https://task.by/press_centr/news/2026/otpusk-zhivotnye-i-strakhovka",
"finalUrl": "https://task.by/press_centr/news/2026/"
```
То есть уже на момент первоначального сбора данных инструмент фиксировал, что запрошенный URL статьи фактически привёл на страницу архива, а не на саму статью — Lighthouse-отчёт по этой «странице» на самом деле аудировал список новостей, а не контент статьи. Рабочий вариант той же статьи существует только с завершающим слэшем: `https://task.by/press_centr/news/2026/otpusk-zhivotnye-i-strakhovka/` (200 OK, отдаёт корректный контент статьи) — именно так оформлены все внутренние ссылки на статьи в самом шаблоне сайта (`href="/press_centr/news/2026/otpusk-zhivotnye-i-strakhovka/"`).

**Объяснение:** Компонент детального просмотра новости в Bitrix при обращении к URL статьи без завершающего слэша не выполняет ожидаемый редирект «добавить слэш и остаться на той же странице» (как это происходит для остальных разделов сайта, например `/about` → `/about/`, `/person/auto/osago` → `/person/auto/osago/`), а вместо этого сбрасывает путь до `/press_centr/news/{текущий_год}/` — то есть до архива текущего календарного года, независимо от того, к какому году относится сама статья.

**Бизнес-влияние:** Любая внешняя ссылка, репост в соцсетях/мессенджерах или URL, введённый вручную без завершающего слэша, приводит пользователя не на ожидаемую статью, а на список новостей текущего года — статья «теряется» без вывода ошибки (не 404, что было бы понятнее пользователю, а тихая подмена контента).

**SEO-влияние:** Внешние бэклинки на статьи, набранные без завершающего слэша (частый вариант при ручном копировании URL или старых публикациях), теряют релевантность — Google видит редирект на совершенно другую по смыслу страницу (архив, а не статья) и может расценить это как soft-404 или сигнал плохого качества связывания; при этом сама статья лишается веса, накопленного по такой ссылке.

**Рекомендация:** Исправить логику компонента детального просмотра новости, чтобы URL без завершающего слэша 301-редиректил на тот же путь с добавленным слэшем (стандартное поведение Bitrix, как для остальных разделов), а не на архив текущего года.

### 6.2 Не экранированные пробелы и кириллица в href PDF/DOC-вложений

**Серьёзность:** Medium

**Затронутые страницы:** как минимум `/person/auto/osago` (раздел «Прикреплённые документы»); тот же паттерн вложений используется на других продуктовых страницах.

**Доказательство:**
```html
<a href="/upload/iblock/adf/Указ 701.pdf">
<a href="/upload/iblock/5fa/Список ТС (Приложение 2).pdf">
```
Прямой запрос по этому «сырому» href безуспешен:
```
$ curl -sL -o /dev/null -w "%{http_code}" "https://task.by/upload/iblock/adf/Указ 701.pdf"
→ ошибка разбора URL (пробел трактуется как разделитель)
```
Тот же файл доступен и отдаёт `200 OK` только после ручного percent-encoding:
```
$ curl -sL -o /dev/null -w "%{http_code}" "https://task.by/upload/iblock/adf/%D0%A3%D0%BA%D0%B0%D0%B7%20701.pdf"
→ 200
```

**Объяснение:** Файл на сервере существует и физически доступен, но в атрибуте `href` он указан «как есть» — с литеральным пробелом и кириллицей вместо percent-encoded URL. Браузеры сами исправляют это при клике, но формально значение атрибута не является валидным URL, из-за чего его не могут корректно обработать: строгие парсеры/валидаторы, боты нехарактерных для браузера типов (некоторые краулеры, антивирусные сканеры ссылок, почтовые клиенты при пересылке ссылки), инструменты автоматизированного QA/аудита (в том числе наш собственный `curl`, использованный в этом аудите).

**Бизнес-влияние:** Незаметно для обычного пользователя в браузере, но потенциально ломает интеграции, автоматический мониторинг битых ссылок и т.д.

**SEO-влияние:** Незначительное для ранжирования HTML-страницы, но сами файлы (Указ, заявления, списки ТС) могут хуже индексироваться Google как отдельные документы, а имена файлов не несут описательных ключевых слов на латинице/транслите (сравните: `Указ 701.pdf` и `Cpisok-TS.doc` — непоследовательное именование).

**Рекомендация:** На уровне серверного вывода компонента «Прикреплённые файлы» приводить путь к файлу к percent-encoded виду перед вставкой в `href` (в Bitrix это делается штатной функцией `rawurlencode` для сегментов пути); в целом рекомендуется переименовывать загружаемые файлы в транслитерированные ЧПУ-имена без пробелов на этапе загрузки в административную часть.

## 7. Контент

### 7.1 Полностью дублирующийся контент между родительским разделом и первой дочерней страницей

**Серьёзность:** Critical

*(Данная проблема подробно описана в разделе 1.2 «Метаданные» — здесь она отражена как отдельная content-проблема, так как выходит за рамки одних лишь title/H1: дублируется 100% контента страницы.)*

**Затронутые страницы:**
- `https://task.by/person` ≡ `https://task.by/person/property`
- `https://task.by/corporate` ≡ `https://task.by/corporate/transport`

**Доказательство:** Побайтовое сравнение полного HTML (`diff`) обеих пар страниц показывает расхождения только в 16 строках, все из которых — динамические токены сессии (`bitrix_sessid`, `PHPSESSID`, `captcha_sid`). Размер файлов идентичен (110 017 байт и 108 247 байт соответственно, побайтово одинаков в обеих версиях каждой пары).

**Объяснение / бизнес- и SEO-влияние / рекомендация:** см. п. 1.2 выше.

### 7.2 Историческая непоследовательность именования архивных URL новостей

**Серьёзность:** Low

**Затронутые страницы:** архив новостей за 2020–2021 годы.

**Доказательство:** В `sitemap-iblock-2.xml` архивные разделы называются словами, а не цифрами:
```
https://task.by/press_centr/news/two-thousand-twenty/...
https://task.by/press_centr/news/two-thousand-twenty-one/...
```
тогда как более новые разделы используют обычный числовой формат:
```
https://task.by/press_centr/news/2022/...
https://task.by/press_centr/news/2023/...
https://task.by/press_centr/news/2024/...
```

**Объяснение:** На каком-то этапе структура ЧПУ для годовых архивов была изменена с англоязычной транслитерации числа на цифровой формат, старые разделы остались в прежнем виде.

**Бизнес-влияние:** Отсутствует практически — старые новости 2020–2021 годов имеют низкую актуальность.

**SEO-влияние:** Минимальное — непоследовательность URL усложняет читаемость структуры сайта при ручном анализе, но не является технической ошибкой (URL рабочие).

**Рекомендация:** Низкий приоритет; при следующей реструктуризации раздела новостей желательно унифицировать архивные пути к единому цифровому формату с настройкой 301 со старых на новые.

## Приложение: проверенные и не подтвердившиеся гипотезы

Для полноты картины — что было целенаправленно проверено и **не оказалось проблемой**:

- **www / non-www и http / https дублирование домена:** несмотря на то, что `robots.txt` содержит устаревшую директиву `Host: www.task.by`, реальная канонизация домена настроена корректно — `http://task.by/`, `https://www.task.by/` и `http://www.task.by/` все отдают `301 → https://task.by/` (без www). Дублирования контента на уровне домена не обнаружено (см. проблему 5.4 — это лишь «мусорная» строчка в конфигурационном файле, без реального эффекта).
- **hreflang:** отсутствует на сайте, но это ожидаемо и не является проблемой — сайт одноязычный (ru-RU), для одноязычных сайтов hreflang не требуется; аудит Lighthouse (`hreflang`, score 1) подтверждает отсутствие ошибок по этому пункту.
- **Индексируемость (`is-crawlable`) и валидность `robots.txt`:** по данным Lighthouse (`is-crawlable`, `robots-txt` — score 1 на всех 25 страницах) страницы не заблокированы от индексации, а сам `robots.txt` синтаксически валиден.
- **Наличие alt-атрибутов у изображений:** проблем не найдено — 100% изображений на всех проверенных страницах имеют непустой `alt` (см. раздел 3).
